# Backend authorization

Liminal is open source. Treat every browser, downloaded HTML copy and launcher as untrusted. Public Supabase keys identify the project; they are not administrator credentials. A launcher version, origin check or embedded secret cannot authorize privileged writes.

The database and Edge Functions verify identity and the current database role for each privileged action. Changes to a client's local owner flag, username, role or user metadata cannot upgrade the account. Older RPC signatures keep working only within the caller's actual permissions.

## Enforced permissions

| Action | Backend requirement |
| --- | --- |
| Announcement, What's New, app availability | Owner or PRESTON, including the legacy setting RPC |
| Channel creation, edits and deletion | Admin or higher |
| Channel speak restrictions | Owner or PRESTON |
| Staff-role management | Co-owner or higher, strictly lower target and assigned role |
| Password resets | Admin or higher, another account strictly below the caller's rank; Owner and PRESTON accounts are protected |
| Kick and timeout | Mod or higher, strictly lower target; Mod timeout maximum remains two hours |
| Ban and unban | Manager or Co-owner/Owner/PRESTON, strictly lower target; Admin variants cannot bypass this through the old dashboard |
| Profile changes | Active account editing its own presentation fields; identity and privilege fields require authorized server operations |
| Message reactions and DM read receipts | Only the verified caller's identity may be changed |
| Message ownership, timestamps, deletion and reply attribution | Enforced or generated by the server; clients cannot create unlabelled system messages |
| Forum posting and edits | Channel speak permissions, account timeouts, global controls, length and blocked-word rules |
| Storage writes | Active account and the existing ownership/staff rules |
| Drive uploads | Mod or higher; create-only writes are atomic |
| Drive replacement, file management and raw multipart | Admin or higher |

Browser roles have no schema-creation, table-truncation or trigger-management privileges. Private helpers are outside the exposed API; new service-only RPCs explicitly revoke browser execution. Keep service keys, R2 credentials and provider keys exclusively in server configuration.

## Validation and remaining audit work

`npm test` runs 80 SQL permission checks, all 81 password-reset role combinations, negative authentication tests and the existing deployment/Drive checks. The rollback-only SQL regression file can also verify the deployed PostgreSQL database without keeping fixture accounts or changing live settings.

This authorization pass addresses the audit's three high-severity findings and the legacy moderation, reaction impersonation, forum-control, banned-upload and Drive-overwrite findings. The audit's separate privacy/availability findings remain: existing DM attachments use public media URLs; Drive's public endpoint still exposes trash metadata/downloads, and R2 public URLs need a separate private-storage design; guest AI rate-limit failures still fail open. Do not describe the audit as fully resolved until those are addressed.

Supabase also reports that [leaked-password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) is disabled. Intentional signed-in RPCs are flagged by the [function-execution advisor](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable); their actual authorization is verified by the role tests, rather than treating an advisor warning as proof of a bypass. Browser execution is revoked from trigger-only functions and anonymous account deletion.

Previously issued Drive signed URLs retain their existing permissions until their 15-minute expiry. Newly issued create-only URLs require the atomic condition.

Do not loosen server checks to make an old client appear compatible. Update the client to match the authorized action instead.
